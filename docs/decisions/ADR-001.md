# ADR-001: Use Synchronous Communication for Request Submission

## Context

When an employee submits a help request, they need to know whether the request was stored successfully or whether something went wrong.

The communication between the user interface and backend could be synchronous or asynchronous.

## Decision

Use synchronous communication between the user interface and backend when submitting a request.

## Reasoning

The employee needs an immediate success or failure response. This prevents the user interface from showing a request as submitted before the backend confirms that it was stored successfully.

If a request requires approval, the approval can happen later and does not need to block the initial submission.

## Alternatives Considered

Asynchronous communication was considered. It could allow the user interface to continue without waiting for the backend, but the employee would not immediately know whether the request was successfully stored.

## Consequences / Trade-offs

- The employee receives a clear success or failure response after submitting a request.
- The employee must wait for the backend and database to respond.
- If the request cannot be stored, the submission is rejected and the employee is asked to try again later.
